## 第 2 章　总体架构

### 2.1 完整数据流 `[已定]`

以 R53 的修正版为准（理解层已前置到第一层）：

```text
输入分辨率（720p~1080p，用户可调）
  │
  ├─ 浅层细节路：Conv 3x3 ×2，保留输入分辨率的高频信息
  │
  └─ 理解层（第一层激活，轻量）〔运行时分辨率随主干缩放，非固定 540p；见 2.2.4 实现修订〕
       ├─ 场景理解 → 全局条件向量
       ├─ 退化理解 → 退化类型 + 空间分布图
       ├─ 意图理解 → 艺术风格 + UI 掩码
       └─ 策略决策 → 路由条件 + 旁路条件 + 量化条件
  │
  └─ 下采样（2x/3x/4x，用户可调）→ 180p~540p
       └─ 低分辨率主干（全帧、不分块）
            ├─ 空间注意力（窗口 8×8/16×16/32×32，用户可调）
            ├─ 三级路由 MoE（专家数 16~64，Top-K 2/4）
            │    ├─ 第一级：组级路由（基于理解层的退化空间分布图）
            │    ├─ 第二级：簇内路由（基于理解层的场景标签）
            │    └─ 第三级：质量门控（基于理解层的 UI/边缘检测）
            ├─ Engram 条件记忆（分层：通用/游戏/用户，基于理解层的场景标签选择分区）
            └─ mHC 残差连接（基于理解层的退化程度动态调整约束强度）
  │
  └─ 两路在输入分辨率空间融合
  └─ 自适应上采样（网络内部固定 2x + 轻量缩放）
  └─ 固定输出分辨率（2160p/1440p）

输出 = 双三次上采样 + 主干低频残差 + 浅层高频残差 + 旁路修正残差
```

**核心理解**（R51）：理解层负责"看懂"，低分辨率主干负责"理解结构、退化类型、纹理先验"，浅层特征负责"保留细节"，两者在输入分辨率空间融合后，再上采样到固定输出分辨率。

> **R51 原始数据流**：理解层位于"低频结构路 → 下采样至 270p~540p"**之后**；R53 用户指出"理解层作为第一层激活的模型，应该准确激活后续专家，所以很明显应该放模型第一层"，理解层被前置到与浅层细节路并行的位置，在 540p 空间运行。此处采用 R53 版本。

### 2.2 理解层（始终激活，最高智能）`[已定]`

#### 2.2.1 职责

理解层不直接重建像素，输出的是条件、先验和决策（R51）：

| 元问题 | 具体内容 | 错误后果 |
|---|---|---|
| 这是什么？ | 场景类型、物体语义、纹理类别 | 路由到错误专家 |
| 退化是什么？ | 模糊、噪声、压缩伪影、锯齿 | 用错重建策略 |
| 该保留什么？ | 创作意图、艺术风格、UI文字 | 抹平创作者表达 |
| 该怎么做？ | 路由决策、旁路激活、量化选择 | 算力分配错误 |

#### 2.2.2 架构（R51）

```text
理解层
  ├─ 共享认知核心（始终激活，所有输入都经过）
  │    └─ 基础特征提取 + 全局上下文建模
  ├─ 场景理解分支
  │    ├─ 全局语义编码　├─ 物体级语义　└─ 区域级语义
  ├─ 退化理解分支
  │    ├─ 退化类型分类　├─ 退化程度估计　└─ 退化空间分布
  ├─ 意图理解分支
  │    ├─ 艺术风格识别　├─ UI/文字检测　└─ 创作意图推断
  └─ 策略决策分支
       ├─ 路由决策　├─ 旁路决策　└─ 量化决策
```

#### 2.2.3 为什么必须前置（R53）

| 如果理解层后置 | 如果理解层前置 |
|---|---|
| 专家层无法获得条件，路由是盲目的 | 专家层根据退化类型和场景条件精准激活 |
| 旁路无法预知哪些 Token 质量敏感 | 旁路根据理解层的 UI/边缘检测结果提前准备 |
| Engram 检索没有场景上下文 | Engram 根据理解层的场景标签选择对应分区 |
| mHC 残差约束没有退化程度参考 | mHC 根据退化程度动态调整约束强度 |

> 记录中的表述：理解层是"大脑"，专家层是"手脚"。大脑必须在手脚动之前做出决策。

#### 2.2.4 参数效率策略

R51 与 R53 给出的策略合并如下：

| 策略 | 效果 | 来源 |
|---|---|---|
| 低秩分解 | 参数量降低 50%~70% | R51 / R53 |
| 跨层参数共享 | 与浅层细节路共享底层特征 | R51 |
| 多任务学习 | 一个理解层输出四组条件 | R51 |
| 多任务共享底层 | 场景/退化/意图/策略共享同一特征提取器 | R53 |
| 知识蒸馏 | 从 DINOv2/SAM/CLIP 蒸馏理解能力 | R51 |
| Engram 辅助 | 存储已知原型，减少理解层参数量 | R51 |
| 注意力池化 | 压缩为全局条件向量，减少后续模块输入维度 | R51 / R53 |
| 输入降采样后再理解 | 理解层在 540p 或 720p 空间运行，而非全分辨率 | R53 |

**推荐**（R53）：理解层在 **540p 空间**运行，参数量控制在总参数的 **15%~20%**，始终激活但轻量。

> **实现修订** `[已修正]`
>
> 上面这条推荐在实现中被替换，原因如下：
>
> 1. **固定 540p 是数量级畸变的根因。** 理解层是稠密计算（算力 ∝ N × dim²），
>    540p 的 token 数是 Low 档主干（180p）的 9 倍。实测「固定 540p + dim=128」时，
>    理解层算力占**完整主干**（当时口径：窗口注意力 + 共享 FFN + 私有专家；
>    该口径后经 issue #5 再次补全，见下方修订）的比例为：
>
>    | 档位 | Low | Middle | High | XHigh | Max |
>    |---|---|---|---|---|---|
>    | 占比 | **2724%** | 491% | 97% | 32% | 12% |
>
>    即低档位理解层比整个主干还贵 27 倍。
>
> 2. **「参数占比 15%~20%」与「给专家留够算力」不可兼得。** 理解层稠密
>    （F/P ∝ N），主干是稀疏 MoE（F/P ∝ K/专家数），二者参数-算力比不同。
>    若强求参数占比，**算力最弱的档位反而需要更大的理解层**，形成反向约束。
>    以 Max 档为例，要把理解层参数占比提到 10%，它就要吃掉完整主干约 30% 的算力。
>
> **实现采用的替代方案**：
>
> - 理解层分辨率**随主干缩放**（`understanding_scale = 1.0`），不再固定 540p
> - 约束改为**算力占比 ≤ 35%**，分母为完整主干（口径后经 issue #5 再次补全）
> - 通道数由主干派生（`understanding_dim_ratio = 1.25`），不为每档手工指定
>
> 修订后实测算力占比 **0.80%~2.97%**（跨度 3.7 倍），畸变消除；但理解层**参数**占比
> 仍为 8.31% → 1.59%（随档位下降），低于本节原定的 15%~20%，此项作为已知限制保留。
> 详见 `README.md`「对设计文档 2.2.4 的一处修订」与 `待决问题清单.md`。
>
> **口径二次修订（issue #5）**：以上占比的分母已再次补全。原先只含「窗口注意力 +
> 共享 FFN + 私有专家」，漏掉了 `fuse`、`HighPrecisionBypass`、`bypass_proj`、
> `main_upsample`、`upsampler` 以及 MoE 内部的共享专家——这些路径**在输入分辨率
> 上执行**，开销随分辨率线性增长，是重建路径的大头。补全后 Low 档主干由
> 2.9 G 升至 **44.2 G**（13.6 倍），占比由 4.7%~12.9% 降至 **0.80%~2.97%**，
> 且**趋势发生反转**（旧口径随档位递减 12.3%→4.7%，新口径递增 0.80%→2.97%），
> 原因是分母的主要成分从「主干分辨率上的注意力/FFN」变成了「输入分辨率上的重建路径」。
>
> 这条修订对上面的判断有实质影响：既然真实占比远低于早期认知，"理解层太贵必须砍"
> 的结论不成立，`understanding_dim_ratio = 1.25` 有较大上调空间可供后续实验探测。

### 2.3 低分辨率主干 `[已定]`

主干承载全部重计算。R52 修正后，主干分辨率不再直接指定，而是由**输入分辨率 ÷ 下采样倍数**决定：

| 档位 | 输入分辨率 | 下采样 | 实际主干分辨率 |
|---|---|---|---|
| Low | 720p | 4x | 180p |
| Middle | 810p | 3x | 270p |
| High | 900p | 3x | 300p |
| XHigh | 1080p | 3x | 360p |
| Max | 1080p | 2x | 540p |

**空间注意力（单帧）** `[已定]`（R51）：

- 窗口大小：16×16 或 32×32（R52 后改为用户可调 8×8/16×16/32×32）
- 多尺度窗口：8×8 + 16×16 + 32×32 三尺度并行
- 轴向注意力：水平 + 垂直两个方向，覆盖全图
- 线性色彩空间：训练和推理都在线性 RGB 空间进行

**为什么必须下采样** `[已定]`（R12）：

1. Transformer 的注意力复杂度是 O(N²)
2. 显存带宽是比算力更硬的瓶颈
3. 低分辨率下更容易建模全局信息
4. 与 MoE、Engram、W4A8 的协同

记录给出的量化依据（R12）：下采样到 270p（480×270），像素数降到 **12.9 万**，token 数减少 **16 倍**；注意力矩阵规模从 O(207万²) 降到 O(12.9万²)，**计算量降低 256 倍**。

### 2.4 三级路由 MoE `[已定]`

#### 2.4.1 三级路由语义（R21 修正后）

```text
Token 特征
  ├─ 第一级：组级路由 → 低精度专家簇（W4A8）
  ├─ 第二级：簇内路由 → 低精度专家（W4A8）
  └─ 第三级：质量门控 → 高精度旁路（FP16/W8A8）
        ├─ 质量敏感 Token：走旁路，高精度重建
        └─ 质量不敏感 Token：不走旁路，只依赖低精度专家输出
```

> **原始设计**（R19）：第三级为"零专家槽位（Token-Level Skip）"，对简单 Token 直接跳过专家计算。R21 用户提出"让一二级的专家实现低精度量化，再由高精度零专家实现高质超分"，第三级被重新定义为**质量门控 → 高精度旁路**。R21 的评述：这实际上是**把"跳过"改成了"旁路"**——不是不计算，而是走一条轻量、高精度、专注于质量重建的旁路。

**为什么用多层路由而非全分散路由**（R19）——全分散路由在 270p 特征图（约 12.9 万 Token）上的三个问题：

1. **路由开销大**：12.9 万次独立路由决策，路由网络本身成为计算瓶颈
2. **决策碎片化**：相邻 Token 属于同一纹理区域，却可能被路由到不同专家，专家输出在空间上不连续，融合后产生伪影
3. **专家利用不均**：平坦区域大量 Token 集中在少数"通用专家"上，造成路由坍塌

预期收益（R19）：

| 指标 | 全分散路由 | 多层路由 | 改善 |
|---|---|---|---|
| 路由决策数 | 12.9 万 | 约 8000 + 簇内细化 | 16 倍减少 |
| 路由网络 FLOPs | 高 | 低 | 降低 60%~70% |
| 专家激活熵 | 低（易坍塌） | 高（簇间均衡） | 显著改善 |
| 平均激活专家数 | Top-2 固定 | 动态 0~2 | 降低 30%~50% |
| 空间连续性 | 差 | 好 | 伪影减少 |
| 专家分化程度 | 低 | 高 | 参数效率提升 |

实现注意（R19）：组大小建议从 4×4 或 8×8 开始（270p 下 4×4 组约对应 120×68 个组）；簇应按退化类型或纹理频率聚类，可用 K-Means 初始化或加入簇间分化损失；组级和簇级需分别做负载均衡；第一级建议用 Gumbel-Softmax 软路由，第二级用标准 Top-K 硬路由。

### 2.5 Engram 条件记忆（分层）`[已定]`

```text
Engram 表
  ├─ 通用层（全局共享，10~15MB）
  │    ├─ 基础边缘方向模板　├─ 基础纹理原型
  │    └─ 常见 UI 控件形态　└─ 常见字体字形
  ├─ 游戏层（每游戏特化，5~15MB）
  │    ├─ 该游戏特有纹理风格　├─ 该游戏 UI 字体和控件
  │    └─ 该游戏渲染特征　　　└─ 该游戏特效模式
  └─ 用户层（可选）
       ├─ 用户偏好锐度模式　└─ 用户自定义纹理先验
```

**检索与融合**：

```text
Token 特征
  ├─ 通用层检索 → 基础先验
  ├─ 游戏层检索 → 特化先验
  └─ 融合（加权求和 + 门控）→ 最终纹理先验
```

**分层动机**（R43）：通用 Engram 存在"多而不精"问题。用户指出"engram 最佳的选择是针对每款游戏进行预训练，这意味着适配难度大幅增加，通用模型虽然泛化性强但多而不精"，由此设计为通用层 + 游戏层分工。

**与路由的协同**（R19）：Engram 的 N-Gram 哈希检索天然适合组级路由——对每个空间组，用其 N-Gram 特征哈希检索 Engram，直接得到该组的退化类型标签，作为第一级路由的先验，使路由网络不需从头学习。

**NTC 理念的借鉴**（R28，NTC 本身已被否决）：Engram 不存储完整纹理原型，而是存储低维潜在向量（如 16 维 INT8），检索后经过轻量 MLP 解码；解码器与 MoE 私有专家共享，避免独立存储。

> **R52/R53 未再提及 Engram 的通用/游戏/用户三层划分**，但 R53 数据流中仍保留"Engram 条件记忆（分层：通用/游戏/用户，基于理解层的场景标签选择分区）"。三层划分保留为有效设计。

#### 2.5.1 容量规范：Engram 不宜过大 `[已定]`（实现阶段补充）

**口径：Engram 表与模型参数分开计算、分开报告。**

| 项 | 定义 |
|---|---|
| 模型参数量 | 参与逐 token 计算的可训练参数，**不含** Engram 表 |
| Engram 表 | 经 N-Gram 哈希确定性寻址的查找表，**不进入每 token 的矩阵乘预算** |
| 占比 | 表条目数 ÷ 主干参数量 |

此口径与前沿实践一致：DeepSeek V4.1-Flash 报告为「**196B Engram 表** 对 **552B 主干**」（约 35.5%）；Qwen3.8-Flash-Next 的表被明确描述为 "deterministically addressed and do not enter the per-token matrix-multiplication budget"。

**规范：Engram 不宜过大。**

1. **容量错配**——权重矩阵实现的是可泛化的变换，查找表实现的是输入到输出的直接映射。在固定容量预算下，分配给记忆的每一分都从泛化能力中扣除；同等字节的权重带来的能力提升远高于同等字节的表。
2. **稀疏更新**——N-Gram 哈希的命中分布是长尾的：少数高频条目被反复更新，大量条目几乎从不命中，那些条目存的是初始化噪声而非有效知识，却照样占用常驻空间。
3. **可能退化为查表机**——若表大到足以"记住"训练集的具体模式，梯度下降会优先走这条捷径（记忆比学规律收敛快），表现为训练 loss 很低而验证泛化差，即模型失去应有的智能。

DeepSeek 的 Engram 论文对此给出了正式结论：神经计算（MoE）与静态记忆（Engram）之间存在 **U 型 scaling law**，容量分配存在最优点，**单纯增大 Engram 不带来收益**。

**参考区间（非硬约束）**：DeepSeek V4.1-Flash 约 35.5%，Qwen3.8-Flash-Next 明显更高（表与主干量级接近），说明最优比例本身仍在探索中。本项目的具体取值由对照实验确定，**不在设计阶段写死**。

### 2.6 mHC（记录中称"残差压制"）`[已定]` `[存疑：译名，见 9.3]`

- Sinkhorn-Knopp 归一化约束残差传播
- 限制梯度范数，保障低精度训练稳定性
- 抑制噪声和压缩伪影，保留高频纹理
- 支持深层网络平滑收敛

> **核实注**：mHC 的全称实为 **Manifold-Constrained Hyper-Connections（流形约束超连接）**，其机制是把残差混合矩阵投影到 Birkhoff 多胞形（双随机矩阵），目的是恢复恒等映射性质、抑制训练不稳定，**而非"压制残差"**。记录中"Sinkhorn-Knopp 归一化约束残差传播"的技术描述方向正确（Sinkhorn-Knopp 正是双随机矩阵投影算法），仅"残差压制"这一概括有偏差。详见《待决问题清单》2.2 修正 2。

R53 补充：mHC 根据理解层输出的**退化程度动态调整约束强度**。

### 2.7 高精度旁路（质量保障）`[已定]`

```text
旁路输入：低精度专家输出 + 浅层细节特征 + 方向估计
  ├─ 边缘重建子模块：方向性卷积 + 边缘残差（FP16）
  ├─ 纹理重建子模块：高频残差 + 纹理记忆（FP16）
  ├─ 1×1 Conv（通道压缩）
  ├─ 3×3 DWConv（空间细节恢复）
  ├─ 1×1 Conv（通道恢复）
  └─ 残差连接
输出：高精度残差，叠加到低精度专家输出上
```

| 参数 | R51 值 | R21 值 |
|---|---|---|
| 参数量占比 | 总参数量的 8%~12% | 总参数量的 5%~10% |
| 激活范围 | 10%~20% 的质量敏感 Token | 10%~20% 的 Token |
| FLOPs 上限 | — | 不超过总 FLOPs 的 15% |

**高低精度分工的逻辑**（R21）：

- 低精度专家承担"量"：一级、二级专家处理退化建模和特征变换（压缩伪影去除、噪声抑制、纹理分类与路由、通用特征提取），这些任务**对绝对精度不敏感，对特征方向敏感**。W4A8 的量化误差表现为"特征轻微偏移"，而不是"结构破坏"。
- 高精度旁路承担"质"：第三级旁路处理最终质量敏感的重建（文字边缘锐化、UI 控件边界、高频纹理细节、颜色精度校正），这些任务**对量化误差极度敏感**。W4A8 在文字区域会产生笔画畸变，在 UI 区域会产生边缘模糊，在颜色渐变区域会产生色带。

**质量门控的触发信号**（R21）：建议多信号融合——边缘梯度强度（Sobel 响应）、局部对比度、Engram 检索到的退化类型标签、路由熵（熵高说明该 Token 不确定，需要旁路保障）。

### 2.8 自适应上采样与输出 `[已定]`（R52 / R53）

R52 最初设计为"PixelShuffle 整数倍 + 轻量缩放"：

```text
主干输出（低分辨率特征）
  ├─ 2x：PixelShuffle(2)
  ├─ 2.4x：PixelShuffle(3) + 轻量缩放
  ├─ 2.67x：PixelShuffle(3) + 轻量缩放
  └─ 3x：PixelShuffle(3)
```

R53 参照 DLSS 修正为**网络内部固定 2x + 轻量缩放对齐输出**：

```text
输出分辨率固定（2160p/1440p）
  ├─ 输入 1080p → 下采样至 270p → 主干 → 上采样 2x → 1080p → PixelShuffle 2x → 2160p
  ├─ 输入 900p  → 下采样至 270p → 主干 → 上采样 2x → 900p  → 缩放至 1080p → PixelShuffle 2x → 2160p
  └─ 输入 720p  → 下采样至 270p → 主干 → 上采样 2x → 720p  → 缩放至 1080p → PixelShuffle 2x → 2160p
```

**理由**（R53）：避免为每个超分倍数训练独立的上采样权重。网络只需学习一个 2x 上采样映射，缩放由轻量后处理（1×1 Conv + 双三次插值）完成。这与 DLSS 的"固定倍数网络 + 动态输入分辨率"策略一致。

**与 DLSS/FSR 对齐的模式表**（R52）：

| 模式 | 输出分辨率 | 输入分辨率 | 超分倍数 |
|---|---|---|---|
| 超高质量 | 2160p | 1080p | 2x |
| 质量 | 2160p | 900p | 2.4x |
| 平衡 | 2160p | 810p | 2.67x |
| 性能 | 2160p | 720p | 3x |

输入分辨率对算力的影响（R52）：900p 输入算力降低约 30%，810p 降低约 45%，720p 降低约 55%。

### 3.1 抗锯齿与细节保留：一对根本矛盾 `[已定]`

| 层面 | 能力 | 局限 | 后果 |
|---|---|---|---|
| 270p 主干 | 全局结构理解，边缘方向推断 | 低频结构，但高频已丢失 | 下采样丢失了锯齿的精确像素位置 |

### 3.5 真实物理现象保留 `[已定]`（R65）

用户提出的问题（R65）："准确来讲不是分区，而是通过现实真实的光影来解决模型只学习了游戏劣质光影、光照导致的智商问题，典型的就是电线、下雨的雨丝、雨丝落地溅起的水花、扬起的灰尘或雪，这些经常会被当做噪点被抹去"。

记录中的分析：模型在游戏数据上训练时，**把"游戏引擎的渲染缺陷"当成了"应该去除的退化"**，而不是"应该保留的物理细节"。

**为什么游戏数据会导致这种误判**（R65）：

| 现象 | 游戏中的表现 | 模型误判 |
|---|---|---|
| **电线** | 细长、高对比度、锯齿明显 | 被当作"高频噪声"或"锐化伪影"抹去 |
| **雨丝** | 半透明、快速运动、颗粒感强 | 被当作"压缩伪影"或"传感器噪声"去除 |
| **雨滴溅起水花** | 粒子效果、闪烁、低分辨率 | 被当作"锯齿"或"闪烁伪影"平滑掉 |
| **扬起的灰尘/雪** | 大量小颗粒、随机分布 | 被当作"颗粒噪声"或"压缩块"抑制 |
| **真实光影** | 柔和的阴影过渡、体积光 | 被当作"模糊"过度锐化 |

**解决方向**：

**1. 数据层面——引入真实物理现象**：

| 物理现象 | 数据来源 | 训练目标 |
|---|---|---|
| 雨丝 | 真实雨天摄影、视频 | 学会保留雨丝，而非抹除 |
| 水花 | 高速摄影、水滴特写 | 学会保留溅射细节 |
| 灰尘 | 逆光摄影、沙漠/工地场景 | 学会保留空气中的颗粒 |
| 雪 | 真实雪景、微距雪花 | 学会保留雪花形态 |
| 电线 | 城市街景、电力设施摄影 | 学会保留细长结构 |
| 体积光 | 晨雾、教堂光束、森林光柱 | 学会保留光影层次 |
| 真实阴影 | 自然光摄影、肖像 | 学会保留柔和过渡 |

记录中的关键：这些数据不是用来"超分"的，而是用来让模型**理解什么是真实物理细节**，从而在游戏画面中区分"引擎伪影"和"物理现象"。

**2. 训练层面——物理感知损失**：

```text
L_total = L_recon + λ1 * L_physics + λ2 * L_artifact_suppression
```

| 损失项 | 作用 |
|---|---|
| L_recon | 重建质量 |
| L_physics | 物理现象保留（雨丝、灰尘、雪、电线） |

`L_physics` 需要**物理现象掩码**：训练数据中标注"哪些区域是雨丝/灰尘/雪"，损失函数只对这些区域计算保留损失。

**3. 理解层升级——从"领域识别"到"物理理解"**：

```text
理解层
  ├─ 物理现象理解分支（新增）
  │    ├─ 这是什么物理现象？（雨/雪/灰尘/电线/光）
  │    ├─ 这是真实细节还是渲染伪影？
  │    └─ 该保留什么？该去除什么？
  ├─ 退化理解分支
  │    ├─ 真实退化（模糊/噪声/压缩）
  │    └─ 渲染伪影（锯齿/闪烁/颗粒）
  └─ 策略决策分支
       ├─ 保留物理现象　├─ 去除真实退化　└─ 抑制渲染伪影
```

理解层需要学会区分"**物理高频**"和"**伪影高频**"：前者要保留，后者要抑制。

**4. 架构层面——引入"物理专家"**：

| 专家类型 | 职责 |
|---|---|
| 雨丝专家 | 保留雨丝的线状结构 |
| 水花专家 | 保留溅射的颗粒细节 |
| 灰尘/雪专家 | 保留空气中的悬浮颗粒 |

**评估指标**（R65）：伪影误判率——把伪影当物理细节保留的比例，目标 <10%。

## 第 4 章　量化策略

### 4.1 分层混合量化总表 `[已定]`

以 R52 的修正版为准（专家层由"W4A8 或三值"改为确定的三值量化）：

> **核实注（已修正）**：记录将本方案称为"**DeepSeek 式**分层混合量化"，并把 W4A8 归因于 DeepSeek。经核实：**DeepSeek 公开的是 FP8 混合精度训练 + W8A8（FP8）推理**，即权重与激活均为 **FP8** 格式，**并非 INT8，也从未提出或公开 W4A8**。DeepSeek-V3 技术报告的原文表述为"我们设计了一个 FP8 混合精度训练框架"，采用 1×128（激活）与 128×128（权重）的细粒度分块量化。
>
> 因此本文档**已去除"DeepSeek 式"前缀**，统称"分层混合量化"。
>
> **格式体系需区分**：DeepSeek 的 **FP8** 是浮点格式，本文档使用的 **INT8/W4A8/三值** 是定点/整型格式，两者不是同一体系。本文档中的 **W8A8 一律指 INT8**，与 DeepSeek 的 FP8-W8A8 不可混用同一缩写。详见《待决问题清单》2.2 修正 1。

| 模块 | 量化配置 | 理由 |
|---|---|---|
| Engram 记忆表 | FP16 / INT8 | 静态知识检索对精度敏感，禁止三值 |
| 理解层 | FP16 / W8A8 | 始终激活，错误级联放大，禁止三值 |
| MoE 第一级组路由 | FP16 / W8A8 | 粗决策，错误级联放大，禁止三值 |
| MoE 第二级簇内路由 | W8A8 | 中等敏感度，禁止三值 |
| 主干注意力 / 共享专家 | W8A8 | 基础特征提取，精度要求高，禁止三值 |
| **一级/二级私有专家** | **三值量化（Q3 性能，Q3 一半体积）** | 参数量大，误差容忍度高 |
| 高精度旁路 | **FP16** | 文字、UI、边缘、颜色精度，禁止三值 |
| 输出重建层 | FP16 / W8A8 | 直接决定像素质量 |
| mHC 残差连接 | W8A8 | 数值稳定性要求高 |

> **R51 原始表述**：一级/二级私有专家为"**W4A8 或三值量化**"，理由为"参数量大，误差容忍度高，三值优先试点"。R52 用户指出"三值量化的性能介于 Q3 和 Q4 之间，可以保留 Q3 性能但体积为 Q3 的一半左右"，专家层由此确定为三值量化。

> **实现注（旁路行）** `[已实现]`
>
> 表中「高精度旁路 = FP16」是**推荐值**，实现中已放宽为可配置项
> `config.bypass_quant`，可选 **W8A8 / FP8 / FP16 / FP32**，默认仍为 FP16（质量优先）。
> 经用户确认：旁路**不强制 FP16**，FP8 的精度损失在一定程度上可接受。
> `TERNARY` / `W4A8` 会被 `validate()` 拒绝——旁路是质量保障路径，不接受激进位宽。
>
> 接线范围：`HighPrecisionBypass` 内部 6 个卷积 + `bypass_proj`，共 7 个，
> 权重与输入激活都做伪量化（实现见 `src/sr/quant.py`）。
>
> **两个实测结论**（`tests/test_quant.py` 可复核，旁路输出相对 FP32 的偏差）：
>
> | 方案 | 相对偏差 | 说明 |
> |---|---|---|
> | FP16 | 1.8e-05 | 精度最高 |
> | W8A8 (INT8) | 9.5e-04 | 均匀 8 位 |
> | FP8 (E4M3) | 5.2e-03 | **精度低于 W8A8** |
>
> 即在本项目的权重动态范围下，**FP8 的精度反而低于 INT8**：E4M3 只有 3 位尾数，
> 而 INT8 是均匀 8 位量化。FP8 的价值在于动态范围与硬件吞吐，不在精度。
> 因此「旁路用 FP8 省带宽」这一取舍需以实测精度损失为前提，不能默认它优于 W8A8。
>
> 另需注意：当前是**伪量化仿真**（投影到目标格式后转回原 dtype 计算），
> 可用于精度评估与 QAT，但省不了显存与带宽；那取决于后续的量化导出与 Vulkan 后端。

**关键保障**（R51）：

- 离群值抑制：Fused Iter-smooth 逆向平滑
- QAT：W4A8 / 三值必须配合量化感知训练
- 知识蒸馏：FP16 教师模型引导量化学生模型恢复细节
- 权重对称 INT4：避免负 scale 导致 INT8 路径权重组爆炸

### 4.2 三值量化（-1 / 0 / +1）`[已定]`

#### 4.2.1 定位（R52）

| 量化方式 | 比特/权重 | 体积（相对 FP16） | 性能定位 |
|---|---|---|---|
| FP16 | 16 | 100% | 基准 |
| W8A8 | 8 | 50% | 接近 FP16 |
| Q4 | 4 | 25% | 高 |
| **三值** | **~1.58** | **~10%** | **介于 Q3 和 Q4 之间** |
| Q3 | 3 | 18.75% | 中 |
| Q2 | 2 | 12.5% | 低 |

记录中的表述：三值量化约 1.58 bit/权重，体积约为 Q3 的一半，性能介于 Q3 和 Q4 之间。`[存疑]`（无来源，见 9.3）

| 专家数 | FP16 体积 | 三值体积 | 节省 |
|---|---|---|---|
| 16 | 100MB | 10MB | 90% |

#### 4.2.3 实现细节（R51 / R52 / R53）

> **核实风险提示**：以下 Tequila 机制与 ButterflyMoE **均出自 LLM/MoE 领域，与超分无关**（分别见 [arXiv 2509.23809](https://arxiv.org/abs/2509.23809)、[arXiv 2601.13563](https://arxiv.org/abs/2601.13563)）。且 arXiv 精确检索 `"ternary" AND "super-resolution"`、`"ternary" AND "image restoration"` **均为 0 条**——**三值量化在超分领域的应用缺乏公开先例**，属跨领域迁移，风险等级应上调。详见《待决问题清单》2.2 修正 3。

- **Tequila 机制**：将死区权重重新利用为可微动态偏置，离线预计算并融合进 kernel `[存疑]`
- **ButterflyMoE**：专家共享三值原型矩阵 + 不同旋转，256 专家下内存压缩 150 倍 `[存疑]`
  - R27 补充：Jetson Nano 上 64 专家仅 1.9 MB
- **Vulkan 算子**：llama.cpp 的 `TQ2_0` / `TQ1_0`、ExecuTorch 的 `TQ2` 格式已可用
  - R53 给出的依据：llama.cpp Vulkan 后端已合入 `TQ2_0`（2.06 bpw）和 `TQ1_0`（1.6875 bpw）的专用算子，包括 dequant、mul_mat_vec、mul_mm、get_rows；125M 三值模型在 Vulkan 上与 F16 的 top-12 logprobs 完全一致到小数点后四位；728M 模型上 TQ2_0 体积 206MB vs F32 的 2.72GB，压缩比 13.5 倍
  - R53 给出的依据：ExecuTorch 通过 Vulkan 后端实现 BitNet 风格三值权重推理，使用 TQ2 格式（256 个权重压入 66 字节），自定义 kernel 在 linear operator 内部即时解量化
- **QAT**：三值量化必须配合量化感知训练

#### 4.2.4 重要限制：三值在通用计算单元上不省算力 `[已定]`（R32）

> 三值量化省的是**显存和带宽**，不是 FLOPs。通用 GPU 上，三值权重仍需解包为 FP16 参与 SIMD 计算。除非设备支持 `cooperative_matrix` 的 INT8 路径，否则算力不变。

### 4.4 三值量化的技术成熟度 `[存疑]`

> 本节为整理者补充的核实结论，用于界定该方案的风险等级。

**结论：三值量化目前仅在 LLM 领域有实际应用，在超分/图像复原领域尚无公开先例。**

核实依据：

| 检查项 | 结果 |
|---|---|
| Tequila 机制 | 真实存在，arXiv 2509.23809（2025-09-28），**LLM/MoE 领域** |
| ButterflyMoE | 真实存在，arXiv 2601.13563（2026-01-20），**LLM/MoE 领域** |
| arXiv 检索 `"ternary" AND "super-resolution"` | **0 条** |
| arXiv 检索 `"ternary" AND "image restoration"` | **0 条** |
| 视觉领域的三值量化案例 | 图像分类（TernaryCLIP）、医学 ViT（BitMedViT）、扩散生成（RobuQ）——**均非超分** |
| 工程实现 | llama.cpp 的 `TQ2_0`/`TQ1_0` 与 ExecuTorch 的 `TQ2` 均已可用（整理者已直接核对源码确认），但**均为 LLM 推理算子** |

**这意味着什么**：

1. 记录中"三值量化专家层"的设计属于**跨领域迁移**——把 LLM 的权重压缩手段套用到超分任务上
2. 该方案在记录中承担了关键角色：它是"专家数往多的方向走"（2.4.2）和"专家层体积压缩 90%"（4.2.2）的支撑点
3. **超分任务对高频细节和边缘的敏感度远高于 LLM 的 token 分类**。记录自己也指出"W4A8 在文字区域会产生笔画畸变、在 UI 区域会产生边缘模糊"（2.7 节），而三值比 W4A8 更激进
4. 记录中"三值量化性能介于 Q3 和 Q4 之间"这一关键论断**无任何来源**

**建议**：在基座模型验证阶段（6.1）就把三值量化专家层作为**独立验证项**，若画质损失超过阈值则回退到 W4A8 或 W8A8。不宜在架构设计阶段就把它当作既定前提。

**计算量控制的关键手段**（R32）：

| 手段 | 效果 |
|---|---|
| 主干分辨率 | 从 540p 降到 270p，像素数减少 4 倍，注意力 FLOPs 减少 **4 倍**（窗口注意力下 FLOPs ∝ N）`[已修正]` |

| MoE 稀疏激活 | Top-1 平均激活 1 个专家，Top-2 平均 2 个 |
| 三值量化 | **不省算力**（见 4.2.4） |

> **已修正**：R32 原文为"注意力 FLOPs 减少 **16 倍（O(N²)）**"。经重算（5.2.7 第一节），窗口注意力下 FLOPs 对 token 数**线性**，分辨率降 4 倍只能省约 **4 倍**；16 倍是**全局**注意力的数字。R32 同表下一行即主张"用窗口注意力替代全局注意力"，两处互相矛盾。

**进一步压缩的手段与代价**（R32）：

| 措施 | FLOPs 收益 | 画质代价 |
|---|---|---|
| 主干降到 180p | 注意力 FLOPs 再降 2.25× | 结构理解变差 |
| 窗口降到 8×8 | 注意力 FLOPs 降 4× | 全局上下文减弱 |
| FFN 扩展因子降到 1 | FFN FLOPs 再降 50% | 通道混合能力下降 |
| 专家数减半 | MoE FLOPs 降 50% | 退化覆盖变窄 |
| 浅层细节路通道减半 | 浅层 FLOPs 降 50% | 高频细节保留变差 |
| 关闭高精度旁路 | 旁路 FLOPs 归零 | 文字/边缘质量下降 |

**Low 档的极限压缩**（R32）：主干 180p、窗口 8×8、FFN 因子 1、专家 2 个、浅层 8 通道、无旁路，单帧 FLOPs 可压到约 **1.5G**，30fps 只需 **45 GFLOPS**。

#### 5.2.7 算力重算 `[已重算]`

> 本节由整理者按统一计算模型重算。**这是本文档中唯一一处整理者自行计算而非转述记录的内容**，计算脚本与全部假设列于下，可独立复核。

**计算模型与假设**：

```text
每个主干 Block = 窗口注意力 + 共享专家 FFN + Top-K 私有专家

窗口注意力  : QKV+O 投影 8NC²  +  窗口内注意力 4Nw²C     （对 N 线性）
共享专家 FFN: 4N·r·C²                                    （r = FFN 扩展因子）
Top-K 专家  : K × 4N·r·C²
浅层细节路  : 输入分辨率上 2×(DW3×3 + PW1×1)
输出后处理  : 2160p 上 1×1 Conv (C→3)

取 w = 8（窗口边长）、r = 2（FFN 扩展因子）
未计入      : Engram 检索、路由网络、旁路（记录中亦列为独立小项，量级 <2G）
```

**各分辨率 token 数**：

| 分辨率 | 尺寸 | token 数 |
|---|---|---|
| 180p | 320×180 | 57,600 |
| 270p | 480×270 | 129,600 |
| 300p | 533×300 | 159,900 |
| 360p | 640×360 | 230,400 |
| 540p | 960×540 | 518,400 |
| 1080p | 1920×1080 | 2,073,600 |
| 2160p | 3840×2160 | 8,294,400 |

**第一节：稳健结论——窗口注意力是 O(N)，不是 O(N²）**

同一配置（C=48, L=6）下，540p → 270p（N 降 4 倍）：

| 注意力类型 | 540p | 270p | 比值 |
|---|---|---|---|
| 窗口 w=4 | 66.9G | 16.7G | 4.00 倍 |
| 窗口 w=8 | 95.6G | 23.9G | 4.00 倍 |
| 窗口 w=16 | 210.2G | 52.6G | 4.00 倍 |
| **全局注意力** | 309,644.2G | 19,363.5G | **15.99 倍** |

**结论**：窗口注意力下 FLOPs ∝ N，分辨率降 4 倍只能省约 **4 倍**；只有**全局**注意力才是 O(N²)，降 16 倍。R32 同时主张"用窗口注意力替代全局注意力"与"O(N²) 使 FLOPs 降 16 倍"，**这两句互相矛盾**——若已用窗口注意力，就不存在 16 倍的 O(N²) 收益。5.2 节"计算量控制的关键手段"表中该行需按 4 倍理解。

#### 5.2.8 "算力占用低于 50%"的口径统一 `[已统一]`

该约束在记录中有**四种不同口径**，这是它始终无法验证的根源：

| 来源 | 口径 | 问题 |
|---|---|---|
| R3 | **推理时间占帧预算的比例**（60 FPS → 16.7ms 预算；如"8~12ms = 48%~72%"） | 与 FLOPs 口径不可互换，且依赖具体硬件实测 |
| R9 / R14 / R25 / R27 | "**非关键帧**只跑 30%~40% 的计算量，整体算力占用自然低于 50%" | **前提是视频多帧场景**，而 R42 已定为单帧超分，该论证**不再成立** |
| R40 | "旁路激活率 > 25% → 算力占用可能超过 50%" | 仅给出触发条件，未定义占用本身 |
| R51 / R52 | "单帧 FLOPs × 目标帧率 ≤ 可用算力" | 定义清晰，但未说明"可用算力"的取值基准 |

**统一后的定义**（本文档采用）：

```text
算力占用率 = (单帧 FLOPs × 目标帧率) / 设备可用算力

其中：
  单帧 FLOPs   = 按 5.2.7 节模型计算的每帧浮点运算量
  目标帧率     = 30 或 60 fps
  设备可用算力 = FP16 峰值 × 实际利用率
                 （利用率：手机/集显 30%~50%，独显 50%~60%，见 5.2 节）
```

**三条必须同时声明的约束**：

1. **基准帧率**：同一档位在 30fps 与 60fps 下的占用率相差一倍，不可省略
2. **是否含推理之外的开销**：本定义**仅计模型推理**，不含引擎渲染、后处理、数据传输
3. **利用率取值**：必须明确设备实测利用率，不能用理论峰值

**关于"非关键帧"论证的处理**：R9 起沿用的"非关键帧只跑 30%~40%"基于视频假设，**在单帧超分下不成立**。该论证已在本文档中标注为不适用，不作为"算力<50%"的依据。

**统一后的判定**：按此定义与 5.2.7 节的重算值，当前五档配置**均无法满足 60fps 下的 50% 占用**（详见 5.2.7 第六节）。若改以 30fps 为基准，Low 档占用约 36%（253/700），Middle 档约 125%（842/675）——仍只有 Low 档可行。

#### 5.6.1 三套口径的差异根因（已定位）

经逐项复算，三套数值**并非互相矛盾，而是统计范围不同**。差异来自三个因素：

| # | 差异因素 | R28 做法 | R29 做法 | 差额 |
|---|---|---|---|---|
| 1 | **1080p 浅层与融合特征** | 算作 2 个独立特征图（175MB） | 认为融合结果可写回浅层缓冲（记 0MB） | **约 175MB** |
| 2 | **余量** | 单列 100~200MB | 未单列 | **约 150MB** |
| 3 | **权重** | 取 80MB（区间上限） | 取 63MB | **17MB** |
| | | | **合计** | **约 342MB** |

342MB 正好解释"500~550MB"与"600~800MB"之间的差距。**R28 把余量计入了总量，R29 只报基线。**

复算验证：

| 口径 | 逐项复算结果 | 记录原文 | 是否吻合 |
|---|---|---|---|
| R29 | 445.5 MB（不含输入帧缓冲） | 约 500~550MB | ✅ 吻合 |
| R28 | 685 MB | 约 600~800MB | ✅ 吻合 |

|---|---|---|---|---|
| 2160p | 3840×2160 | 50 MB | 530 MB | 1.06 GB |
| 1080p | 1920×1080 | 12 MB | 132 MB | 265 MB |
| 540p | 960×540 | 3 MB | 33 MB | 66 MB |
| 270p | 480×270 | 0.8 MB | 8.3 MB | 16.6 MB |

**用户的核心洞察**（R29）："显存占用按理来讲取决于输入的画面大小，后续的计算很明显显存占用浮动不大"。

**三条架构原则**（R29）：

- **原则一：高分辨率空间只保留"必需"的特征图** — 1080p 空间峰值约 200 MB
- **原则二：所有重计算在 270p 完成** — 270p 空间峰值约 80 MB
- **原则三：2160p 空间只做输出，不做计算** — 2160p 空间峰值 50 MB

#### 5.6.5 降级策略

| 显存预算 | 降级措施 |
|---|---|
| < 1GB | 关闭高精度旁路，全部走 W4A8/三值专家；主干通道数减半；Engram 表缩容至 5MB |
| < 800MB | 下采样到 360p 主干；窗口注意力改为 8×8；专家数减半 |
| < 600MB | 退回 INT8+FP16 稠密模型，放弃 MoE；或接受分块推理（但用户明确不分块） |

**Vulkan 显存优化手段**：

1. 内存别名（Memory Aliasing）：不同张量复用同一块显存，只要生命周期不重叠
2. 原地操作：Conv+BN+ReLU 融合后，输出写回输入缓冲
3. 算子融合：QKV 投影、PixelShuffle 前卷积、后处理 1×1 Conv 全部融合
4. 描述符集复用：避免每帧重新创建描述符
5. 命令缓冲预录制：MoE 的 Top-K 专家分支固定后，可预录制命令缓冲
6. Engram 表常驻显存：INT8 存储，通过 buffer device address 直接访问

### 6.1 总路线：先做对，再做快 `[已定]`（R66）

用户主张（R66）："目前第一部应该是训练一个完整的全精度基座模型看看效果，确保效果可以后再考虑实时速度"。

记录中的表述：基座模型是"天花板"，后续所有优化都是在逼近这个天花板，而不是超越它。

| 如果先做实时优化 | 如果先做全精度基座 |
|---|---|
| 不知道画质上限在哪 | 明确画质天花板 |

#### 6.1.1 基座模型设计原则 `[已定]`

- **全精度**：所有权重 FP16 或 FP32；无量化、无三值、无 INT8；不做 QAT/PTQ；不做剪枝、不做专家裁剪

**训练配置**：

| 配置项 | 建议 |
|---|---|
| 分辨率 | 固定输出 2160p，输入 1080p 起步 |
| 宽高比 | 先 16:9，后续扩展 |
| 领域 | 游戏 + 自然 + 物理现象 |
| 损失 | L1 + LPIPS + 边缘损失 + 频域损失 + 物理感知损失 |

### 6.2 渐进式路由训练 `[已定]`（R20）

用户主张（R20）："先训练一级路由，再细化训练二级三级路由"。

**为什么必须分阶段**——端到端训练时，第三级的离散决策产生高方差梯度，回传到第二级时已经失真；第二级的簇内 Top-K 决策进一步放大方差，第一级组路由几乎收不到有效梯度，结果退化为固定分组。分阶段训练的本质是：每一阶段只让当前路由层学习，冻结其他路由层，梯度传播路径短且稳定。

#### 阶段一：训练第一级组路由 + 共享专家

- **冻结**：第二级簇内路由、第三级门控、专家簇划分
- **训练**：主干特征提取网络、第一级组路由网络、共享专家、所有专家簇
- **路由方式**：组级路由输出 Top-1 专家簇，该簇内所有专家参与计算
- **损失**：`L = L_recon + λ1 * L_group_balance + λ2 * L_cluster_diversity`
- **关键点**：此阶段**不引入第三级门控**，所有 Token 都必须经过专家计算。因为如果早期就允许跳过，组级路由会倾向于把所有 Token 都跳过，退化为恒等映射
- **预期**：组级路由的专家簇选择准确率 70%~80%

#### 阶段二：训练第二级簇内路由

- **冻结**：第一级组路由、第三级门控、主干（可选择性冻结）
- **训练**：第二级簇内路由网络、簇内专家（只激活 Top-K）
- **路由方式**：簇内 Top-2 路由
- **损失**：`L = L_recon + λ1 * L_cluster_balance + λ2 * L_expert_specialization`
- **关键点**：第一级组路由保持冻结但可微，梯度通过它传播到主干但权重不更新；K 值建议从 Top-2 开始，不要一开始用 Top-1；专家特化损失可用专家输出的余弦相似度度量
- **预期**：簇内路由的专家选择熵显著高于随机选择

#### 阶段三：训练第三级质量门控 + 高精度旁路

- **冻结**：第一级、第二级路由、主干
- **训练**：质量门控 + 高精度旁路 + 共享专家微调
- **损失**：重建损失 + 旁路激活率约束 + 旁路重建质量损失
- **关键点**：边缘子模块和纹理子模块分别训练
- **预期**：旁路激活率稳定，旁路 Token PSNR 与未激活 Token 差距 <0.3dB

> **原始设计**（R20）：阶段三为"训练第三级零专家槽位"，目标跳过率 40%~60%。R21 修正为"质量门控 + 高精度旁路"，目标改为旁路激活率 10%~20%。

#### 阶段四（可选）：端到端微调

- **冻结**：无，使用极小学习率（阶段三的 1/10）
- **损失**：重建 + 总负载均衡 + 旁路激活率 + 簇间分化 + 路由一致性
- **关键点**：容易破坏已学好的路由结构；可引入路由一致性损失（微调前后路由决策的 KL 散度）；如果微调后 PSNR 下降，应回退到阶段三

**各阶段资源与预期**（R20，第三级表述按 R21 修正）：

| 阶段 | 训练参数 | 冻结参数 | 显存需求 | 预期 PSNR | 路由准确率 |
|---|---|---|---|---|---|
| 阶段一 | 主干 + 组路由 + 共享专家 + 全簇专家 | 二级/三级路由 | 高（全簇激活） | 基线 | 组级 70%~80% |
| 阶段二 | 簇内路由 + 簇内专家 | 组路由 + 主干 | 中 | +0.2~0.5dB | 簇内熵提升 |
| 阶段三 | 质量门控 + 旁路 + 共享专家 | 组路由 + 簇内路由 | 低 | +0.1~0.3dB | 旁路激活率 10%~20% |
| 阶段四 | 全部（极小 lr） | 无 | 高 | +0.1~0.2dB | 路由稳定 |

**阶段一的显存优化**（R20）：如果显存不足，可将阶段一拆分为 1a（只训练主干 + 共享专家）和 1b（冻结主干，训练组路由 + 簇专家）。

**风险与应对**（R20）：

| 风险 | 应对 |
|---|---|
| 阶段一路由坍塌（所有 Token 选同一簇） | 调大负载均衡损失权重，或引入专家容量因子 |
| 阶段二破坏阶段一的路由 | 冻结组路由，只让梯度通过；或加入组路由一致性损失 |
| 阶段三激活率失控 | 硬约束（超目标值则惩罚加倍），或引入额外重建损失 |
| 阶段四微调退化 | 极小学习率 + 路由一致性损失；仍退化则跳过阶段四 |

### 6.3 理解层训练：迭代蒸馏 + 自我迭代 `[已定]`（R46 / R47 / R51）

```text
冷启动（基座模型蒸馏）
  └─ 教师：DINOv2/SAM/CLIP
  └─ 目标：获得基础视觉理解
       ↓
自我迭代（GRPO + 多目标奖励）
  └─ 模型自己生成超分结果
  └─ 用奖励信号评估质量
  └─ 通过 GRPO 更新理解层
  └─ 目标：突破教师上限
       ↓
再蒸馏
  └─ 教师：自我迭代后的理解层
  └─ 目标：压缩进化后的能力
       ↓
再迭代 → 循环直到边缘效应明显
```

**用户提出的核心逻辑**（R47）："蒸馏模型不可能超过教师模型，所以需要像 LLM 思维链的第一次出现那样（DeepSeek-R1 训练方式），让模型自己迭代，随后继续蒸馏，才能把模型知识、智能密度推向边界"。

**视觉推理链**（R51）：

```text
推理步骤1：这是什么场景？
推理步骤2：退化类型是什么？
推理步骤3：该区域需要什么策略？
推理步骤4：该激活哪些专家？该走高精度旁路吗？
输出：路由决策 + 条件向量
```

**奖励信号**（R47 / R51）：

| 奖励类型 | 衡量内容 | 实现方式 |
|---|---|---|
| 重建奖励 | PSNR/SSIM/LPIPS | 与 GT 对比 |
| 边缘奖励 | 边缘方向一致性 | Sobel 方向误差 |
| 纹理奖励 | 高频能量匹配 | 频域损失 |
| UI奖励 | 文字可读性 | OCR 置信度 |
| 路由奖励 | 路由决策正确性 | 专家分化度 |
| 算力奖励 | 算力效率 | FLOPs 惩罚 |
| 创作意图奖励 | 风格保留度 | 风格分类器 |

记录中的关键：奖励信号不能只有 PSNR。PSNR 高的模型可能过度平滑，丢失创作意图，必须多目标平衡。

**强化学习算法选择**（R47）：

| 算法 | 适用场景 | 特点 |
|---|---|---|
| **PPO** | 稳定训练 | 需要价值网络，显存开销大 |
| **GRPO** | DeepSeek-R1 同款 | 不需要价值网络，适合大模型 |
| **DPO** | 偏好对齐 | 需要成对偏好数据 |
| **自训练** | 简单场景 | 伪标签 + 置信度筛选 |

推荐 GRPO（Group Relative Policy Optimization）：不需要价值网络，显存开销小，适合低显存训练场景。

**每一轮蒸馏什么**（R46）：

| 蒸馏类型 | 蒸馏内容 | 作用 |
|---|---|---|
| **特征蒸馏** | 教师的中间层特征 | 学习通用视觉表示 |
| **注意力蒸馏** | 教师的注意力图 | 学习关注哪些区域 |
| **关系蒸馏** | 教师特征间的相似度矩阵 | 学习语义关系 |
| **logits蒸馏** | 教师的分类输出 | 学习场景/退化分类 |
| **梯度蒸馏** | 教师的梯度信息 | 学习优化方向 |

记录中的说明：每一轮循环可以侧重不同的蒸馏类型。第一轮侧重特征和注意力，后续轮次侧重关系和高层语义。

**边缘效应的识别**（R46）——定量指标：

| 指标 | 含义 | 停止条件 |
|---|---|---|
| **理解层PSNR增益** | 每轮循环后重建质量的提升 | 连续两轮增益 <0.05dB |
| **路由准确率增益** | 路由决策的改善 | 连续两轮增益 <0.5% |
| **退化分类准确率** | 退化理解能力 | 达到95%以上 |
| **蒸馏损失下降** | 与教师的差距 | 连续两轮下降 <1% |
| **验证集综合指标** | 多任务综合表现 | 连续两轮无显著提升 |

**定性判断**：

| 现象 | 含义 |
|---|---|
| 困难样本不再减少 | 理解层已覆盖主要分布 |
| 新增数据不再提升 | 理解层已饱和 |
| 教师与学生差距稳定 | 蒸馏收益递减 |
| 任务特化与通用理解冲突 | 需要调整蒸馏权重，而非继续循环 |

**边缘效应的本质**（R46）：来自两个方向——教师能力上限（学生无法超过教师）与任务分布饱和（已覆盖所有退化类型和场景类型）。应对方式：前者引入更强教师或切换到自训练，后者扩展任务类型或提高任务难度。

**自训练与伪标签**（R46）：

```text
理解层 → 预测伪标签 → 筛选高置信度样本 → 作为新训练数据 → 理解层再训练
```

关键：只保留高置信度伪标签（置信度 > 0.95）；结合一致性正则化；防止确认偏差（用集成模型或 MC Dropout 估计不确定性）。

**8GB 共享内存的用法**（R68）：

| 用途 | 方式 | 效果 |
|---|---|---|
| **优化器状态 Offload** | 将 Adam 的 m/v 放在 CPU 内存 | 显存降低 30%~50% |

**组合效果**（R70）：

```text
           = 约 290MB 显存

80M参数模型：FP16权重 160MB + FP16梯度 160MB + 8-bit Adam 160MB + 梯度检查点后激活 80MB
           = 约 560MB 显存
```

| 主干分辨率 | 270p~360p |
| 专家数 | 16~32 |

**训练时间估算**（R70）：数据量 2万~5万帧；batch size 1（梯度累积到 16~32）；每 epoch 数十小时；总训练时间数周~数月。

#### 6.4.3 INT8 训练的辨析 `[已定]`（R69 → R70）

R69 曾给出"INT8 训练可把可训练参数量从 40M 提升到 60~80M"的结论。**R70 明确否定了这一结论**：

> INT8 QAT 不省显存（优化器状态仍为 FP32），真正省显存的是 8-bit Adam 和梯度检查点；8GB 显存用 FP16 + 8-bit Adam + 梯度检查点 + 梯度累积可训练 80~100M 参数，不需要 INT8 训练。

INT8 的真正适用场景（R70）：

| 阶段 | 精度 | 目的 |
|---|---|---|
| 预训练 | FP16 + 8-bit Adam | 建立基础能力 |
| QAT微调 | FP16 + 伪量化 | 模拟INT8推理误差 |
| 推理部署 | INT8 | 省带宽、省算力 |

#### 6.4.4 低显存训练优化技术汇总 `[已定]`（R51）

| 技术 | 显存收益 | 代价 |
|---|---|---|
| 梯度检查点 | 激活降低 50%~80% | 训练时间 +20%~30% |
| 8-bit Adam | 优化器状态降低 75% | 精度损失极小 |
| LoRA 微调 | 可训练参数降低 90% | 需预训练基础模型 |
| 梯度累积 | 显存与 batch 解耦 | 训练时间线性增加 |
| 混合精度 | 激活降低 50% | 需要 loss scaling |
| 知识蒸馏 | 学生显存降低 50%+ | 需教师模型 |
| GRPO | 不需要价值网络，显存降低 50% | 需要奖励模型 |

**组合效果**（R51）：原本 1.4GB 显存的训练可压到 200MB 以内。

#### 6.5.2 多分辨率训练 `[已定]`（R61 / R62 / R63）

用户提问（R61）："能不能实现同一图片，用多种分辨率训练（720p-1080p-4k-64k）"。

**原理**：一张 HR 图可以生成多个 LR-HR 对——从同一高分辨率真值图下采样得到不同尺度的 LR，HR 固定。

**可变倍数与 LR-HR 对应关系**（R61）：

| 配对 | 输入 | 输出 | 说明 |
|---|---|---|---|
| LR(1080p) → HR(2160p) | 1080p | 2160p | 2x 超分，最高画质 |
| LR(900p) → HR(2160p) | 900p | 2160p | 2.4x，平衡 |
| LR(810p) → HR(2160p) | 810p | 2160p | 2.67x，性能 |
| LR(720p) → HR(2160p) | 720p | 2160p | 3x，最低画质 |

**64K 为什么不现实**（R61）：

| 分辨率 | 像素数 | 显存估算 | 可行性 |
|---|---|---|---|
| 4K | 830万 | 50MB | 可行 |
| 8K | 3320万 | 200MB | 勉强 |
| 16K | 1.33亿 | 800MB | 困难 |
| 32K | 5.3亿 | 3.2GB | 不可行 |
| **64K** | **21亿** | **12.8GB** | **完全不可行** |

**多分辨率训练解决的两个失败模式**（R62）：

- **欠拟合**：模型没见过其他尺度

| 输入 | 模型是否见过 | 后果 |
|---|---|---|
| 1080p | 正常 | 画质良好 |
| 900p | 没见过 | 退化特征不匹配，画质下降 |
| 720p | 没见过 | 严重模糊，模型无法处理 |

- **过拟合**：模型过度适应单一尺度

| 过拟合表现 | 原因 | 在其他尺度上的后果 |
|---|---|---|
| 纹理过度锐化 | 模型记住了1080p的特定高频模式 | 在900p输入上产生不自然锐化 |
| 噪声过度抑制 | 模型记住了1080p的特定噪声分布 | 在720p输入上无法处理更强的噪声 |
| 边缘过度平滑 | 模型记住了1080p的特定锯齿模式 | 在810p输入上产生过度平滑 |
| 路由坍塌 | 所有Token都路由到"1080p专家" | 其他专家得不到训练 |

**多分辨率训练的具体收益**（R62）：

| 输入尺度 | 退化程度 | 对理解层/专家层的意义 |
|---|---|---|
| 1080p | 轻微 | 激活精细纹理专家，旁路激活率低 |
| 900p | 中等 | 激活中等纹理专家，旁路激活率中 |
| 720p | 严重 | 激活强重建专家，旁路激活率高 |

Engram 侧：按分辨率分区，分别存储精细退化、中等退化、严重退化的特征表示。

**损失函数**（R62）：`L_total = L_recon + λ1 * L_scale_consistency + λ2 * L_route_balance`

**训练数据量需求**（R61）：

| 配对 | 建议帧数 | 说明 |
|---|---|---|
| 1080p→2160p | 5000~10000 | 基础2x |
| 900p→2160p | 3000~5000 | 2.4x |
| 810p→2160p | 3000~5000 | 2.67x |
| 720p→2160p | 5000~10000 | 3x，退化最严重 |

**用户提出的训练顺序**（R63）："先用1080p训练，然后再用720p训练，等模型具有一定的理解能力后加入随机多尺度训练，并掺入极端尺寸训练，泛化能力提高应当在模型有一定智能的预训练后期进行"。

| 阶段 | 模型学到的 | 为什么不能跳过 |
|---|---|---|
| 1080p | 基础2x映射、精细退化处理 | 最干净、最易学的尺度 |
| 720p | 更强退化处理、更大感受野 | 在已有基础上扩展 |
| 随机多尺度 | 尺度不变性、条件计算 | 需要前两步的基础 |
| 极端尺度 | 鲁棒性边界 | 需要模型已有足够智能 |

记录中的核心逻辑：模型必须先学会"最简单的任务"，才能在此基础上学习"更复杂的任务"。如果一开始就混合所有尺度，模型会陷入**尺度混乱**——它不知道该学哪个尺度的退化模式，路由网络也会因为信号混杂而坍塌。

**宽高比多样性**（R63）：用户指出"分辨率比例不能局限于16:9，应当把多种比例加进去训练，不然也会欠拟合"。

| 宽高比 | 典型场景 | 分辨率示例 |
|---|---|---|
| 16:9 | 主流游戏、视频 | 1920×1080 |
| 16:10 | 笔记本、部分游戏 | 1920×1200 |
| 21:9 | 带鱼屏、电影级游戏 | 2560×1080 |
| 32:9 | 超宽带鱼屏 | 3840×1080 |
| 4:3 | 老游戏、复古风格 | 1440×1080 |
| 3:2 | 部分移动设备 | 1620×1080 |

为什么宽高比比分辨率更容易导致欠拟合（R63）：

| 维度 | 分辨率 | 宽高比 |
|---|---|---|
| 变化方式 | 整体缩放 | 横纵比变化 |
| 影响 | 退化程度 | 几何结构、纹理方向、物体比例 |
| 欠拟合表现 | 模糊/锯齿处理不当 | 物体变形、纹理拉伸、边缘方向错误 |

记录中的关键判断：分辨率变化是**同构缩放**，宽高比变化是**异构变形**。模型如果只见过 16:9，遇到 21:9 时会错误估计边缘方向、错误处理纹理、错误路由。

**完整训练课程**（R63）：

| 阶段 | 训练内容 | 宽高比 | 目的 |
|---|---|---|---|
| **1** | 1080p → 2160p | 仅16:9 | 建立基础2x能力 |
| **2** | 720p → 2160p | 仅16:9 | 扩展退化处理能力 |
| **3** | 随机多尺度（720p~1080p） | 16:9 + 16:10 | 引入尺度不变性 |
| **4** | 随机多尺度 + 极端尺度（540p/360p） | 多种宽高比 | 增强泛化边界 |
| **5** | 全尺度 + 全宽高比 + 多游戏 | 全部 | 最终泛化 |

#### 6.5.3 多领域训练 `[已定]`（R64）

用户指出（R64）："超分训练也不能局限于游戏，毕竟有些人可能只是单纯想要给图片超分，专精于游戏的话也会导致模型在视频超分、图片超分等其他场景欠拟合、或者过拟合导致破坏原有效果"。

**只训练游戏的失败模式**（R64）：

| 场景 | 游戏模型的行为 | 后果 |
|---|---|---|
| **自然图像** | 过度锐化，把柔和光影当成模糊 | 皮肤、云层、水面出现不自然纹理 |
| **动漫图像** | 把平涂色块当成压缩伪影 | 色块边缘出现锯齿或色带 |
| **视频超分** | 把胶片颗粒当成噪声去除 | 电影感消失，画面塑料化 |
| **医学影像** | 把组织纹理当成噪声抑制 | 诊断细节丢失 |
| **文字截图** | 把字体边缘当成锯齿平滑 | 文字模糊，可读性下降 |
| **老照片** | 把胶片颗粒当成退化去除 | 年代感消失，画面失真 |

**覆盖的领域**（R64）：

| 领域 | 数据来源 | 退化特征 | 训练重点 |
|---|---|---|---|
| **游戏** | 自采 + GameIR-SR | TAA模糊、锐化、压缩 | 抗锯齿、细节保留 |
| **自然图像** | DIV2K、Flickr2K | 光学模糊、传感器噪声 | 真实纹理重建 |
| **视频** | REDS、Vimeo-90K | 运动模糊、压缩伪影 | 时序一致性 |
| **动漫** | 动漫截图、线稿 | 平涂色块、线条 | 线条锐度、色块纯净 |
| **文字/UI** | TextZoom、UI截图 | 锯齿、压缩 | 字形结构、可读性 |
| **医学影像** | 公开医学数据集 | 低剂量噪声、组织纹理 | 诊断细节保留 |
| **卫星影像** | 遥感数据集 | 大气散射、传感器噪声 | 地物边界 |
| **老照片** | 老照片数据集 | 胶片颗粒、划痕 | 颗粒保留、划痕修复 |

**领域采样权重**（R64）：

```python
domain_weights = {
    "game": 0.40,       # 主要目标
    "natural": 0.15,    # 泛化基础
    "video": 0.10,      # 时序泛化
    "anime": 0.10,      # 线条/色块泛化
    "text": 0.10,       # 字形泛化
```

**理解层需要识别领域**（R64）：理解层的场景理解分支必须扩展为**领域理解**分支，输出领域标签 + 领域置信度，与退化理解分支共同驱动策略决策分支。

**Engram 需要按领域分区**（R64）：游戏区、自然区、动漫区、文字区、其他区（医学、卫星、老照片）。

**领域感知的量化敏感度**（R64）：自然图像对量化精度要求高（W4A8 或 W8A8）。

**领域渐进的训练课程**（R64）：

| 阶段 | 分辨率 | 领域 | 目的 |
|---|---|---|---|
| **1** | 1080p→2160p | 游戏 + 自然 | 建立基础2x能力 |
| **2** | 720p→2160p | 游戏 + 自然 + 动漫 | 扩展退化处理 |

**与游戏后训练的关系**：通用模型保证泛化，游戏特化模型通过后训练提升特定游戏表现。

### 6.6 游戏特化后训练 `[已定]`（R33）

用户提出（R33）："那就只能针对不同游戏做专门后训练了"。

**为什么后训练是合理路线**（R33）：

| 维度 | 通用单模型 | 针对游戏后训练 |
|---|---|---|
| 覆盖范围 | 所有游戏，但每类都平庸 | 每个游戏都最优 |
| 算力效率 | 为通用性付出冗余算力 | 算力精准匹配该游戏特征 |
| 画质上限 | 受限于通用退化建模 | 可针对该游戏引擎特化 |
| 训练成本 | 一次大训练 | 多次小后训练 |
| 分发成本 | 单一模型 | 多模型，但可增量下载 |

记录中的核心逻辑：不同游戏引擎的退化特征差异极大。UE5 的 TAA 模糊、Unity 的锐化伪影、Frostbite 的色差、RE Engine 的噪点模式，它们的退化分布完全不同。

**后训练的不是整个模型**（R33）——**只有部分模块需要后训练**：

| 模块 | 是否后训练 | 理由 |
|---|---|---|
| 浅层细节路 | 否 | 通用高频提取，与游戏无关 |
| 主干注意力 | 否 | 通用视觉理解，与游戏无关 |
| 共享专家 | 否 | 通用纹理处理，与游戏无关 |
| **MoE 私有专家** | **是** | 不同游戏退化类型不同，专家需特化 |
| **路由网络** | **是** | 路由决策需适配该游戏的特征分布 |
| **Engram 记忆表** | **是** | UI、字体、图标、纹理模式因游戏而异 |
| **高精度旁路** | **是** | 边缘/文字特征因游戏渲染管线而异 |
| mHC 残差 | 否 | 数值稳定性机制，与游戏无关 |
| 输出重建层 | 微调 | 可小幅微调，适配该游戏色彩空间 |

**后训练参数量**：只占模型总量的 **20%~30%**。这意味着后训练显存需求远低于从头训练、后训练时间从数周降到数小时、可以在 6GB 显存设备上完成。

**后训练的自动化流程**（R33）：

```text
1. 数据采集
   └─ 自动录制该游戏的 1080p 画面 + 引擎原生 4K 帧
   └─ 覆盖不同场景：静态、运动、UI、文字、特效

2. 退化分析
   └─ 分析该游戏的退化类型分布，聚类得到该游戏的退化标签

3. Engram 注入
   └─ 提取该游戏的 UI 元素、字体、图标
   └─ 哈希后写入 Engram 记忆表（可完全自动化）

4. 路由微调
   └─ 冻结主干和共享专家，只训练路由网络和私有专家
   └─ 用该游戏的退化标签监督路由

5. 旁路微调
   └─ 冻结低精度专家，只训练高精度旁路
   └─ 针对该游戏的文字/边缘特征优化

6. QAT 校准
   └─ 用该游戏数据校准量化参数
   └─ 确保三值/INT4 专家在该游戏上不退化

7. 打包分发
   └─ 只分发后训练增量（专家权重 + Engram 表 + 旁路）
   └─ 基础模型保持共享
```

记录中的说明：Engram 注入和路由微调可以**完全自动化**，不需要人工干预；旁路微调可能需要少量人工审核。

**与 DLSS 1.0/2.0 的对比**（R33）：

| 维度 | DLSS 1.0 | DLSS 2.0+ | 本方案 |
|---|---|---|---|
| 训练方式 | 每游戏单独训练 | 通用模型 | 通用基础 + 每游戏后训练 |
| 模型大小 | 每游戏独立 | 单一模型 | 共享基础 + 增量 |
| 泛化能力 | 无 | 强 | 基础通用 + 游戏特化 |

**工程实现要点**（R33）：增量分发、动态加载、多游戏缓存、自动化后训练管线、质量验证。

- **自动化后训练管线**：用游戏内录屏 + 引擎原生 4K 帧作为训练数据；云端 GPU 集群批量后训练；每个游戏后训练时间控制在 2~4 小时；新游戏发布后 24 小时内可支持
- **质量验证**：自动计算该游戏边缘区域/纹理区域 PSNR；人工抽检 UI/文字可读性；如果后训练失败，回退到通用模型

**关于"哪些游戏值得后训练"**（R34）：用户主张"哪些游戏值得后训练不应该由算法开发者决定，而是开源由游戏的创作者、社区、玩家共同努力"。

> **R33 原始设计**：曾按优先级排序（3A 大作/竞技游戏最高、有大量 UI/文字的 RPG 高、独立游戏/老游戏中、像素风/卡通渲染低），并提出"先覆盖 Top 50 热门游戏"。**该开发者单方面决定的排序方式被 R34 用户否定。**

## 第 7 章　部署与集成

### 7.1 Vulkan 全平台部署 `[已定]`（R51 / R53）

- **推理框架**：ExecuTorch Vulkan 后端（支持 INT4/三值权重 + INT8 动态激活）
- **备选框架**：ncnn（仅 INT8，可作过渡）
- **全帧 Dispatch**：不分块，所有 Compute Shader 在全帧特征图上调度
- **INT4/三值解包**：权重以 uint4 或 TQ2 格式打包，在 shared memory 中位操作解包为 INT8
- **MoE 动态分支**：只提交 Top-K 专家的 compute pipeline
- **Engram 哈希查找**：哈希表和记忆表存于设备本地内存，通过 buffer device address 直接访问
- **算子融合**：Conv+BN+ReLU、QKV、PixelShuffle 前卷积全部融合
- **内存别名**：不同张量复用同一块显存，降低峰值
- **Specialization Constants**：同一套 shader 编译出不同档位变体

#### 7.1.1 算子选型 `[已定]`（R53）

| 算子类型 | 推荐方案 | 理由 |
|---|---|---|
| 三值权重矩阵乘 | llama.cpp 的 `TQ2_0` Vulkan shader 实现 | 已在多款 GPU 上验证，精度与 F16 一致，通用性最好 |
| INT8 矩阵乘 | `VK_KHR_cooperative_matrix` + FP16 累加 | 性能远超标准 ALU 循环 |
| 深度可分离卷积 | 标准 Compute Shader | 通用性最好，所有 Vulkan 设备都支持 |
| PixelShuffle | 标准 Compute Shader（shared memory 优化） | 无专用扩展，手写 shader 即可 |
| Engram 哈希查找 | `VK_KHR_buffer_device_address` + 设备本地内存 | 通用性最好，避免 CPU 回读 |

**为什么不依赖厂商专用扩展**（R53）：`VK_QCOM_image_processing3` 确实为 Adreno GPU 提供了超分上采样的硬件加速 gather 指令，性能提升显著，但这是高通专用扩展，其他 GPU 不支持。策略是：基础路径用标准 Compute Shader + `VK_KHR_cooperative_matrix` 保证全平台可运行；如果检测到厂商扩展，则启用厂商加速路径作为**可选优化**，但绝不作为必需依赖。

#### 7.1.2 扩展等级与回退链 `[已定]`

**等级划分**（R51）：

| 等级 | Vulkan 扩展 | 启用特性 |
|---|---|---|
| L3 | `VK_KHR_cooperative_matrix` + FP16 | INT8 矩阵加速 + FP16 累加 |
| L2 | Vulkan 1.2 + FP16 | 标准 Compute Shader + FP16 |
| L1 | Vulkan 1.0/1.1 | FP32，MoE 专家数减半，Engram 缩容 |

**自动选择**（R53）：

```text
设备初始化时：
  ├─ 检测 VK_KHR_cooperative_matrix → 有则启用（性能档 L3）
  ├─ 检测 VK_KHR_buffer_device_address → 有则启用 Engram 零拷贝（L2）
  ├─ 检测 Vulkan 1.2 + FP16 → 标准 Compute Shader（L1）
  └─ 仅 Vulkan 1.0/1.1 → FP32 回退路径（L0）

用户可手动覆盖：强制使用某个等级（用于测试或调试）
```

**厂商扩展优先启用、逐一回退** `[已定]`（R56）：用户提出"厂商拓展优先启用，逐一尝试后回退（一般来讲厂商自己的接口不会对其他家的请求做反应）"。记录设计了四条独立回退链：矩阵乘回退链、权重解包回退链、上采样回退链、Engram 检索回退链。

#### 7.1.3 目标 GPU 覆盖 `[已定]`（R53）

用户主张："目标GPU是全部GPU都能跑（只要能支持Vulkun，拓展等级选性能最好的最高级）"。

| 平台 | 代表 GPU | Vulkan 支持 | 预期等级 |
|---|---|---|---|
| Android 手机 | Adreno 6xx/7xx, Mali-G5x/G7x | Vulkan 1.1~1.3 | L0~L2 |
| iOS/iPadOS | Apple A/M 系列（MoltenVK） | Vulkan 1.1~1.2 | L1~L2 |
| Windows 集显 | Intel Iris Xe, AMD RDNA2 集显 | Vulkan 1.2~1.3 | L1~L2 |
| Windows 独显 | NVIDIA GTX/RTX, AMD RX, Intel Arc | Vulkan 1.2~1.4 | L2~L3 |
| Linux | Mesa 驱动 + 各厂商 | Vulkan 1.2~1.4 | L1~L3 |
| macOS | Apple Silicon（MoltenVK） | Vulkan 1.1~1.2 | L1~L2 |

**最低硬件要求**：显存 512MB 可用（Low 档运行时约 330~380MB）；Vulkan 1.0 以上；FP16 建议支持但不强制；存储基础模型 + 当前游戏增量约 75~85MB。

不支持的设备：仅支持 OpenGL ES 2.0/3.0 的老旧设备。

### 7.2 矩阵运算加速器支持计划 `[已定]`（R54）

用户要求（R54）："把对矩阵运算加速器（英伟达的tensorcore，AMD、英特尔、砺算等的加速单元）的支持加入后续计划"。

#### 7.2.1 各厂商矩阵加速单元概览

| 厂商 | 加速单元 | Vulkan 暴露方式 | 支持精度 | 覆盖设备 |
|---|---|---|---|---|
| **NVIDIA** | Tensor Core | `VK_KHR_cooperative_matrix` + `VK_NV_cooperative_matrix2` | FP16/BF16/TF32/INT8/INT4/FP8 | RTX 20/30/40/50 系 |
| **AMD** | Matrix Core | `VK_KHR_cooperative_matrix` | FP16/BF16/INT8 | RDNA3/RDNA4 |
| **Intel** | XMX | `VK_KHR_cooperative_matrix` | FP16/BF16/INT8 | Arc / Xe-HPG |
| **Qualcomm** | Adreno 矩阵单元 | `VK_KHR_cooperative_matrix`（部分）+ `VK_QCOM_image_processing` | FP16/INT8/INT4 | Adreno 7xx |
| **ARM** | Mali 矩阵单元 | `VK_ARM_tensors` + `VK_KHR_cooperative_matrix` | FP16/INT8 | Mali-G7xx |
| **砺算** | TrueGPU 通用计算单元 | 需验证，预计标准 Compute Shader | FP32/INT32 双发射 | LX 7G100 系列 |
| **Apple** | AMX / GPU 矩阵单元 | MoltenVK 暂不支持 cooperative_matrix | FP16 | M 系列（受限） |

记录中的判断：`VK_KHR_cooperative_matrix` 已在 Vulkan 1.4 中提升为核心 API，NVIDIA、AMD、Intel、Qualcomm、ARM 均已支持，这是全平台矩阵加速的统一入口。`[存疑：见 9.3 核实结果]`

#### 7.2.2 分阶段支持计划

**阶段一：基础矩阵加速（随首个版本发布）**

目标：在所有支持 `VK_KHR_cooperative_matrix` 的设备上启用 INT8 矩阵乘加速。

| 任务 | 说明 |
|---|---|
| 检测 `VK_KHR_cooperative_matrix` | 设备初始化时查询支持的矩阵尺寸和精度 |
| 实现 INT8 矩阵乘 Cooperative Matrix Shader | 主干注意力 QKV 投影、FFN、输出重建层 |
| 实现 FP16 矩阵乘 Cooperative Matrix Shader | 旁路模块、理解层 |
| 保留标准 Compute Shader 回退路径 | 不支持 cooperative_matrix 的设备走 ALU 循环 |
| 算子融合 | QKV 投影 + 注意力 + FFN 合并为少量 Dispatch |

支持设备：NVIDIA RTX 20+、AMD RDNA3+、Intel Arc、Qualcomm Adreno 7xx、ARM Mali-G7xx。
预期收益：INT8 矩阵乘性能提升 2~4 倍，FP16 提升 1.5~3 倍。

**阶段二：三值权重矩阵乘加速**

| 任务 | 说明 |
|---|---|
| 移植 llama.cpp 的 TQ2_0 Vulkan shader | 三值权重解包 + 矩阵乘 |
| 适配专家层动态激活 | 只对 Top-K 专家的权重做矩阵乘 |
| 融合解包与矩阵乘 | 在 shared memory 中解包后直接参与 cooperative matrix |
| ButterflyMoE 旋转支持 | 共享三值原型 + 旋转矩阵的快速计算 |

支持设备：优先 NVIDIA（INT4 Tensor Core）、Qualcomm（INT4 Adreno）、AMD RDNA4（若有 INT4）。
预期收益：专家层权重带宽降低 75%，矩阵乘吞吐提升 2~3 倍。

**阶段三：厂商专用扩展加速（可选优化）**

| 厂商 | 扩展 | 用途 |
|---|---|---|
| Qualcomm | `VK_QCOM_image_processing3` | 硬件加速 gather 指令，用于 PixelShuffle 和上采样 |
| NVIDIA | `VK_NV_cooperative_matrix2` | 更灵活的矩阵尺寸和精度组合 |
| ARM | `VK_ARM_tensors` | 张量操作专用路径，用于 Engram 检索 |
| NVIDIA | `VK_NV_memory_decompression` | 纹理解压，与三值权重解包共用位操作 |

策略：这些扩展作为可选加速路径，检测到则启用，未检测到则走标准路径，绝不作为必需依赖。

**阶段四：砺算科技适配（待合作或社区贡献）**

| 任务 | 说明 |
|---|---|
| 申请开发者样卡 | 或由社区贡献者提供测试设备 |
| 验证 Vulkan cooperative_matrix 支持 | 确认砺算驱动是否暴露该扩展 |
| 验证 FP32/INT32 双发射对矩阵乘的加速 | 编写微基准测试 |
| 适配专用 Shader | 若支持 cooperative_matrix，走标准路径；否则优化 ALU 循环 |
| 贡献给砺算开发者社区 | 作为其"渲推一体"生态的 AI 案例 |

关键：这一步不主动推进，等 Star 有起色后由社区或砺算主动接触。

#### 7.2.3 与现有架构的对接

| 模块 | 矩阵运算 | 加速方案 | 精度 |
|---|---|---|---|
| 理解层 | 注意力 QKV、FFN | FP16 cooperative_matrix | FP16 |
| 主干注意力 | QKV 投影、输出投影 | INT8 cooperative_matrix | W8A8 |
| 共享专家 | FFN | INT8 cooperative_matrix | W8A8 |
| 私有专家 | FFN（三值权重） | TQ2_0 shader + cooperative_matrix | 三值权重 + INT8 激活 |
| 路由网络 | 组路由、簇内路由 | FP16 cooperative_matrix | FP16 |
| 高精度旁路 | 方向性卷积、1×1 Conv | FP16 cooperative_matrix | FP16 |
| 输出重建层 | 1×1 Conv、PixelShuffle | INT8 cooperative_matrix | W8A8 |
| Engram 检索 | 哈希查找（非矩阵） | 不适用 | — |

**矩阵尺寸适配**：

| 厂商 | 典型矩阵尺寸 | 适配策略 |
|---|---|---|
| NVIDIA | 16×16×16, 32×8×16 | 按 16 的倍数对齐通道数 |
| AMD | 16×16×16 | 同上 |
| Intel | 8×16×16, 16×16×16 | 按 16 的倍数对齐 |
| Qualcomm | 16×16×16 | 同上 |
| ARM | 16×16×16 | 同上 |

策略：主干通道数、专家 FFN 扩展维度、理解层隐藏维度全部按 **16 的倍数**对齐。这既适配 cooperative_matrix，也便于三值权重打包。

**降级路径**：

```text
设备初始化：
  ├─ 检测 VK_KHR_cooperative_matrix
  │    ├─ 支持 INT8 → 启用 INT8 矩阵加速（L3）
  │    ├─ 支持 FP16 → 启用 FP16 矩阵加速（L2）
  │    └─ 不支持 → 标准 Compute Shader（L1）
  ├─ 检测厂商专用扩展
  │    ├─ VK_QCOM_image_processing3 → 启用高通上采样加速
  │    ├─ VK_NV_cooperative_matrix2 → 启用 NVIDIA 灵活矩阵
  │    └─ VK_ARM_tensors → 启用 ARM 张量路径
  └─ 均不支持 → FP32 ALU 回退（L0）
```

用户可覆盖：界面中显示当前加速等级，用户可手动切换到更低等级（用于调试或兼容性测试）。

#### 7.2.4 量化策略与加速单元的匹配

| 量化方式 | 最佳加速单元 | 兼容性 |
|---|---|---|
| 三值权重 | NVIDIA INT4 Tensor Core、Qualcomm INT4 | 需 TQ2_0 解包 |
| W4A8 | NVIDIA INT4、AMD RDNA4 INT4 | 需 cooperative_matrix INT4 支持 |
| W8A8 | 所有 cooperative_matrix 设备 | 通用性最好 |
| FP16 | 所有 cooperative_matrix 设备 | 通用性最好 |

#### 7.2.7 厂商扩展优先级与回退链（R56）

用户主张（R56）："厂商拓展优先启用，逐一尝试后回退（一般来讲厂商自己的接口不会对其他家的请求做反应）"。

**各厂商扩展优先级**：

| 优先级 | 厂商 | 扩展 | 用途 | 启用条件 |
|---|---|---|---|---|
| 1 | NVIDIA | `VK_NV_cooperative_matrix2` | 更灵活的矩阵尺寸和精度组合 | 检测到即启用 |
| 1 | NVIDIA | `VK_NV_memory_decompression` | 三值权重解包加速 | 与 TQ2_0 共用位操作 |
| 2 | Qualcomm | `VK_QCOM_image_processing3` | 硬件加速 gather，用于 PixelShuffle 和上采样 | 检测到即启用 |
| 3 | ARM | `VK_ARM_tensors` | 张量操作专用路径，用于 Engram 检索 | 检测到即启用 |
| 4 | AMD | `VK_AMD_*`（如有矩阵相关） | 待确认 | 检测到即启用 |
| 5 | Intel | `VK_INTEL_*`（如有矩阵相关） | 待确认 | 检测到即启用 |
| 6 | 砺算 | 待自研驱动发布后确认 | 预计矩阵加速 | 检测到即启用 |
| — | 通用 | `VK_KHR_cooperative_matrix` | INT8/FP16 矩阵加速 | 厂商扩展不可用时启用 |
| — | 通用 | `VK_KHR_buffer_device_address` | Engram 零拷贝访问 | 标准回退 |

注意：NVIDIA 的两个扩展可以同时启用，不互斥。`cooperative_matrix2` 用于矩阵乘，`memory_decompression` 用于权重解包，两者协同工作。

**四条独立回退链**——每个功能模块有独立的回退链，不是全局一刀切：

```text
矩阵乘
  ├─ 尝试 VK_NV_cooperative_matrix2（NVIDIA）
  ├─ 尝试 VK_KHR_cooperative_matrix（全平台）
  ├─ 尝试标准 Compute Shader + FP16
  └─ 回退 FP32 ALU

三值权重解包
  ├─ 尝试 VK_NV_memory_decompression（NVIDIA）
  ├─ 尝试 TQ2_0 标准 Compute Shader（全平台）
  └─ 回退 INT8 解包 + ALU 计算

PixelShuffle / 上采样
  ├─ 尝试 VK_QCOM_image_processing3（Qualcomm）
  ├─ 尝试标准 Compute Shader + shared memory 优化
  └─ 回退双三次插值

Engram 哈希查找
  ├─ 尝试 VK_ARM_tensors（ARM）
  ├─ 尝试 VK_KHR_buffer_device_address（全平台）
  └─ 回退 CPU 回读 + 上传
```

关键：每个模块独立回退。NVIDIA 上矩阵乘走 cooperative_matrix2、上采样走标准 Compute Shader；Qualcomm 上矩阵乘走 cooperative_matrix、上采样走 image_processing3。混合路径是正常的。

**用户可见的加速等级**：

```text
┌─────────────────────────────────────────┐
│  加速状态                                │
│  ├─ 矩阵乘: NVIDIA cooperative_matrix2  │
│  ├─ 权重解包: NVIDIA memory_decompression│
│  ├─ 上采样: 标准 Compute Shader         │
│  ├─ Engram: buffer_device_address       │
│  └─ 综合等级: L3（厂商专用）            │
│                                          │
│  [手动切换加速等级]                      │
└─────────────────────────────────────────┘
```

用户可覆盖：允许手动强制使用某个等级（用于调试或对比测试），但默认自动选择最优。

**输入结构**（R42 修正后）：

```c
typedef struct {
    const void* color;          // 低分辨率颜色输入（单帧）
    const void* uiMask;         // 可选：UI 区域掩码
    uint32_t width, height;
    uint32_t outWidth, outHeight;
    uint32_t format;
    float sharpness;
    // 注：原 antialiasing 字段已移除 —— 实现侧（SRConfig）从未消费该参数，
```

**引擎集成**（R37）：UE 插件、Unity 插件、通用注入三条路径。

**良性循环四阶段**：

```text
1. 修改最初的代码 → 社区 Fork 基础架构，针对特定游戏/硬件/场景做修改
```

### 9.2 记录内部的冲突与未收敛项

#### 冲突 1：训练资源约束与基座模型规模目标相互矛盾 `[冲突]`

| 轮次 | 表述 |
|---|---|
| R67 | 用户："本地训练撑死了给6G显存外加10G内存，我也没钱租算力" |
| R67 | 记录结论：6GB 显存"无法从头训练你设计的完整基座模型（预计 50M+ 参数）" |
| R66 | 记录给出基座训练需"约 40~80GB"显存、"单卡 A100 约 2~4 周" |
| R70 | 记录结论：8GB 显存"可以训练 80~100M 参数模型" |
| R71 | 用户："基座模型参数量越大越好"；记录给出"6GB 显存本地训练 → 基座 50M~100M"、"只有 6GB 显存 → 基座 100M，云端租 A100 训练" |

**矛盾点**：R67 明确"没钱租算力"，R71 的建议仍以"云端租 A100"为推荐路径。R67 给出的可行路径是"用免费云端（Colab/Kaggle）训练小规模基座"，但免费额度（Colab 每天数小时、Kaggle 每周 30 小时）与 R66 估算的"单卡 A100 约 2~4 周"训练量之间，记录**未做可行性核算**。

#### 冲突 2：档位表的"专家数"含义前后不一致 `[已统一]`

| 版本 | 列名 | Low 档取值 | 实际含义 |
|---|---|---|---|
| R51（及 R30/R31） | 专家数**/簇** | `4 / 2` | 每簇 4 个专家、共 2 个簇（合计 8） |
| R52 | 专家数 | `16` | 专家总数 16 |

**矛盾点**：R52 将"专家数"改为专家总数并大幅提升（Low 从合计 8 变为 16，Max 从 64 变为 64 但 Top-K 从 2 升到 4），但**显存预算一栏与 R51 完全相同**（Low 330~380MB、Max 760~850MB）。专家数翻倍而显存不变，与 R52 自身"专家数越多，三值量化的收益越大"的论述方向一致，但**未给出重新核算的过程**。

**统一方式**：已确定统一口径为**专家总数**，R51 版档位表已按"专家数/簇 × 簇数"换算（见 5.1.0 节），并据此重算了各档显存（见 5.6.3 节）。

#### 冲突 3：主干分辨率变化，但 FLOPs 表未同步更新 `[已重算]`

R52 把分辨率策略改为"输入分辨率 ÷ 下采样倍数"，导致实际主干分辨率相比 R51 下降：

| 档位 | R51 主干 | R52 推算主干 | 变化 |
|---|---|---|---|
| Low | 270p | 720p ÷ 4x = **180p** | 下降 |
| Middle | 270p~360p | 810p ÷ 3x = **270p** | 下降 |
| High | 360p | 900p ÷ 3x = **300p** | 下降 |
| XHigh | 360p~540p | 1080p ÷ 3x = **360p** | 下降 |
| Max | 540p | 1080p ÷ 2x = **540p** | 不变 |

**矛盾点**：R51 与 R52 的 FLOPs 表**逐字相同**（Low 4G / Middle 10G / High 19G / XHigh 32G / Max 54G）。而 R32 明确指出"主干分辨率是最大杠杆——从 540p 降到 270p，注意力 FLOPs 减少 16 倍（O(N²)）"。Low 档主干从 270p 降到 180p、High 从 360p 降到 300p，FLOPs 理应下降，但表未更新。

**该表已按统一模型重算，结果见 5.2.7 节。** 重算发现的问题比"未同步更新"更严重：

1. R32 同时主张"用窗口注意力"与"O(N²) 降 16 倍"，**两句互相矛盾**（窗口注意力下 FLOPs 对 N 线性，只能省 4 倍）
2. 原表**无法用单一模型复现**（Max 档即使取最小窗口也差 2.4 倍；MoE 列反解出的层数在 0.24~0.60 间波动）
3. 重算值比记录值高 **2.1~12.8 倍**
4. **可行性判定反转**：按重算值，没有任何一档能在目标设备上同时满足 60fps 与"算力占用<50%"

#### 冲突 4：三张显存估算表数值不一致 `[已统一]`

| 来源 | 结论 |
|---|---|
| R28 | 总运行时显存 **800MB~1GB**；同轮最终估算表合计 **约 600~800MB** |
| R29 | 基线约 **500~550MB**，峰值不超过 **650MB** |
| R51/R52 | 各档 **330~380MB 至 760~850MB** |

R28 与 R29 相差约 150~250MB，两者都基于"270p 主干 + 1080p 浅层 + 2160p 输出"的同一架构。

**差异根因已定位**（详见 5.6.1 节）：三套数值**并非矛盾，而是统计范围不同**——R28 把 1080p 浅层与融合算作两个独立特征图（+175MB）、单列余量（+150MB）、权重取上限（+17MB），三项合计 342MB，正好解释差距。

**统一方式**：已采用"**基线 + 浮动**"两段式表述（见 5.6.2 节），基线约 460MB、峰值约 530MB，并明确标注是否含余量与输入帧缓冲。

#### 冲突 5："算力占用低于 50%"的基准定义不一致 `[已统一]`

| 来源 | 口径 |
|---|---|
| R3 | 推理时间占帧预算的比例（60 FPS → 16.7ms 预算；如"8~12ms = 48%~72%"） |
| R9 / R14 / R25 / R27 | "非关键帧只跑 30%~40% 的计算量，整体算力占用自然低于 50%"——**基于关键帧/非关键帧的视频假设** |
| R40 | "旁路激活率 > 25% → 算力占用可能超过 50%" |
| R51 / R52 | 约束式改为"单帧 FLOPs × 目标帧率 ≤ 可用算力" |

**矛盾点**：R9 起多次出现的"非关键帧只跑 30%~40%"论证，其前提是**视频多帧场景**（关键帧/非关键帧划分）。但 R42 已明确本项目为**单帧超分，移除全部时序组件**。该论证在 R42 之后**不再成立**，然而 R14、R25、R27 的框架版本中仍保留此句。

**统一方式**：已给出单一可验证定义（见 5.2.8 节）：

```text
算力占用率 = (单帧 FLOPs × 目标帧率) / 设备可用算力
```

并规定必须同时声明**基准帧率**、**是否含推理外开销**、**利用率取值**三项。"非关键帧"论证已标注为不适用于单帧超分。

#### 冲突 6：INT8 训练结论被推翻 `[已定]`

R69 曾给出"INT8 训练可把可训练参数量从 40M 提升到 60~80M"。**R70 明确否定**：INT8 QAT 不省显存（优化器状态仍为 FP32），真正省显存的是 8-bit Adam 和梯度检查点；8GB 显存用 FP16 + 8-bit Adam + 梯度检查点可训练 80~100M 参数，不需要 INT8 训练。此条已在正文 6.4.3 按 R70 处理。

#### 冲突 7：R67 / R68 同轮内参数量口径不一致

| 轮次 | 不一致处 |
|---|---|
| R67 | "6GB显存可以训练 **10~20M** 参数的小模型" vs 配置表中"参数量 **10~15M**（极限）" |
| R68 | "60~80M" vs "25~40M 模型的具体架构参数" |

**五项需要修正的偏差**：

1. **W4A8 归因错误（证伪）**——DeepSeek 公开的是 **FP8 混合精度训练 + FP8(W8A8) 推理**，从未公开 W4A8。记录中"DeepSeek 式分层混合量化"的命名依据不成立。技术方案本身不受影响，本文档已去除该前缀，统称"分层混合量化"。
2. **mHC 译名偏差**——实为"流形约束超连接"，机制是恢复恒等映射性质，而非"压制残差"。
3. **Tequila 与 ButterflyMoE 的应用域**——两者真实存在且确为三值量化，但**均属 LLM/MoE 领域，与超分无关**。且 arXiv 精确检索 `"ternary" AND "super-resolution"`、`"ternary" AND "image restoration"` **均为 0 条**：**三值量化在超分领域的应用缺乏公开先例**（详见 4.4 节）。
4. **DLSS 4.5 性能损耗无依据**——官方从未公布第二代 Transformer 的位宽或算力开销，无评测佐证。该主张在记录中被当作既定事实用于推导架构决策，应降级为"未经证实的观察"。
5. **砺算科技的两项细节无证据**——"Vulkan 驱动基于 Mesa"无任何证据；"通用计算单元"仅有官网营销表述。**附带发现**：砺算官网明确列出 **NRSS 超分辨率**产品，与本文档主题直接相关，记录中未提及。
6. **算力表口径错误（新增，见 5.2.7）**——R32 的 FLOPs 表内部不自洽，且"窗口注意力"与"O(N²) 降 16 倍"互相矛盾。本文档已按统一模型重算，重算值远高于记录值。

**整理者独立验证的两项**（直接抓取源码，非转述）：

- `ggml.h` 中确实定义 `GGML_TYPE_TQ1_0 = 34`、`GGML_TYPE_TQ2_0 = 35`
- llama.cpp Vulkan 着色器生成器的 `type_names` 数组确实包含 `"tq1_0"`、`"tq2_0"`

**结论**：记录 R53 关于"llama.cpp Vulkan 后端已合入 TQ2_0/TQ1_0 专用算子"的核心主张**成立**；但记录中"125M 三值模型与 F16 精度完全一致到小数点后四位"、"728M 模型压缩比 13.5 倍"两个具体数值**未能独立验证**。

### 9.4 溯源状态

如 0.2 节所述：记录中 243 处 `[reference:N]` 引用标记均无 URL；145 次网页抓取的内容全部为 0 字节；33 次网页搜索仅保留结果条数。**因此本设计文档中所有外部技术论断（DLSS 4.5 架构、砺算科技现状、llama.cpp 的 TQ2_0 精度数据、ButterflyMoE 的 150 倍压缩、三值量化 1.58 bit 等）均无法回溯到原始出处。**

**3.2 推荐算子选型**

| 算子类型 | 推荐方案 | 理由 |
|---|---|---|
| **三值权重矩阵乘** | llama.cpp 的 TQ2_0 Vulkan shader 实现 | 已在多款 GPU 上验证，精度与 F16 一致，通用性最好 |
| **INT8 矩阵乘** | `VK_KHR_cooperative_matrix` + FP16 累加 | Vulkan 1.4 已提升为核心 API，性能远超标准 ALU 循环[reference:6] |
| **深度可分离卷积** | 标准 Compute Shader | 通用性最好，所有 Vulkan 设备都支持 |
| **PixelShuffle** | 标准 Compute Shader（shared memory 优化） | 无专用扩展，手写 shader 即可 |
| **Engram 哈希查找** | `VK_KHR_buffer_device_address` + 设备本地内存 | 通用性最好，避免 CPU 回读 |
